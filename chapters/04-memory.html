Robot memory

By default every call starts from zero. A checkpointer gives R-80 a memory per conversation, and middleware keeps that memory from overflowing.

Checkpointerthread_idSummarization

// THE CONCEPT

LLMs are stateless: they only know what's in the messages you send them. Memory means saving those messages between calls, and keeping them small enough to fit in the model's context window.

// YOUR ROBOT GAINS

  • Remembers instructions across turns
  • Separate conversations per mission
  • Long missions without hitting the context limit

// KEY TERMS

  • Checkpointer: saves the state after each step
  • thread_id: which conversation to continue
  • Context window: max tokens a model can read at once

Threads and checkpointers

A checkpointer saves the graph state after every step. A thread_id picks which saved conversation to continue. Same thread: R-80 remembers. New thread: blank slate. Like save slots in a video game.

def ask(agent, text: str, thread: str) -> None:
    config = {"configurable": {"thread_id": thread}}
    result = agent.invoke({"messages": [{"role": "user", "content": text}]}, config)
    print(f"[{thread}] OPERATOR: {text}\n[{thread}] R-80: {result['messages'][-1].text}\n")

InMemorySaver is lost when the script stops. Swap it for SqliteSaver or PostgresSaver to persist missions on disk. The API stays the same.

When the context overflows

Every tool call adds messages. On a long patrol the history grows until it no longer fits in the context window, or just gets slow and expensive. Pick Long patrol in the simulator above and watch the token gauge.

Trim

Drop the oldest messages. Cheap, but the robot forgets early instructions.

Summarize

SummarizationMiddleware replaces old messages with a short summary and keeps the last N intact.

Store outside

Put long-term facts (maps, preferences) in a Store and retrieve them when needed.
