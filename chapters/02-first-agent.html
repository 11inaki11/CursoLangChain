Your first robot agent

R-80 gets a brain (a model and a system prompt), hands (tools) and a manual it can read (RAG). Three steps, one agent.

2a · Brain2b · Tools2c · RAG

// THE CONCEPT

create_agent() takes three ingredients: a model (who thinks), a system prompt (who it is and its rules) and tools (what it can do). RAG is simply one more tool.

// YOUR ROBOT GAINS

  • A brain you can swap in one line
  • An identity and rules it always follows
  • Actions in the world, and knowledge from its manuals

// KEY TERMS

  • Provider: who runs the LLM
  • System prompt: permanent instructions
  • Tool: function the LLM may call
  • RAG: search your docs, then answer

2a · The brain: provider + system prompt

Creating an agent means making two big decisions before any tool exists: which LLM runs underneath (the provider) and who the robot is (the system prompt).

Decision 1 · The provider

The provider is the company or server that runs the underlying LLM: Google, OpenAI, Anthropic, DeepSeek, Mistral, or your own GPU with Ollama. LangChain puts all of them behind the same interface, so the rest of your agent never changes. Switch tabs and compare: only the model line changes.

from langchain.agents import create_agent

# Option A: universal one-liner (recommended)
from langchain.chat_models import init_chat_model
model = init_chat_model("google_genai:gemini-3.7-flash")

# Option B: the provider's own class (exposes provider-specific options)
from langchain_google_genai import ChatGoogleGenerativeAI
model = ChatGoogleGenerativeAI(model="gemini-3.7-flash")

# Identical for every provider:
agent = create_agent(model=model, system_prompt="You are R-80, a lab robot.")

Option A · init_chat_model("provider:model")

One import for every provider. Change a string (or an env var) to swap brains. You can even pass the string straight to create_agent(model="…").

Option B · the provider's class

ChatOpenAI, ChatAnthropic… Same interface, plus provider-only settings. Needs that provider's package.

How to choose? Compare them on the same robot:

Cloud or local? Cloud models are faster and smarter out of the box. A local model on your own GPU is private and has no per-call cost, but tool calling is only reliable with capable models.

Decision 2 · The system prompt

The system prompt is a hidden first message (SystemMessage) that the model reads before every turn. The operator never sees it, but it shapes everything: who the robot is, what it knows about itself, which rules it must never break, and how it formats its answers. Without it, the model is a generic chatbot that doesn't even know it has wheels.

🪪 Role

"You are R-80, a lab robot built in 1986."

📏 Facts & limits

"Your max payload is 2.5 kg."

🚧 Rules

"Always scan before picking something up. Never leave the lab."

🗣 Style & format

"Max 2 sentences." or "Reply only with JSON."

Same model, same question, three system prompts:

SYSTEM_PROMPT = (
    "You are R-80, a friendly lab robot built in 1986. "
    "You speak like a retro computer terminal. Answer in at most 2 sentences."
)

BRAINS = [
    DEFAULT_MODEL,             # Gemini (cloud)
    "deepseek:deepseek-chat",  # DeepSeek (cloud)
    LOCAL_MODEL,               # Ollama (local / SSH tunnel)
]

if __name__ == "__main__":
    for brain in BRAINS:
        try:
            agent = create_agent(model=get_model(brain), system_prompt=SYSTEM_PROMPT)
            result = agent.invoke(
                {"messages": [{"role": "user", "content": "Boot up and introduce yourself."}]}
            )
            print(f"\n[{brain}]\n{result['messages'][-1].text}")
        except Exception as exc:  # missing key, Ollama not running...
            print(f"\n[{brain}] skipped -> {exc}")

2b · Tools: give it hands

A tool is just a Python function. The @tool decorator reads its name, type hints and docstring and shows them to the LLM, which then decides when to call it and with which arguments. The function itself runs in your code, and its return value goes back to the LLM as an observation.

def make_robot_tools(robot: str) -> list:
    """Build the toolset for one robot. Reused by every later chapter."""

    @tool
    def move_to(location: str) -> str:
        """Drive the robot to a location. Valid: dock, shelf_a, workbench, door, shelf_b."""
        return WORLD.move_to(robot, location)

    @tool
    def scan_surroundings() -> str:
        """Look around: items and robots at the current location."""
        return WORLD.scan(robot)

    @tool
    def check_battery() -> str:
        """Read the battery level (%)."""
        return WORLD.battery(robot)

    @tool
    def pick(item: str) -> str:
        """Pick up an item at the current location with the gripper."""
        return WORLD.pick(robot, item)

    @tool
    def place() -> str:
        """Place the item being held at the current location."""
        return WORLD.place(robot)

    @tool
    def charge() -> str:
        """Charge the battery to 100%. Only works at the dock."""
        return WORLD.charge(robot)

    return [move_to, scan_surroundings, check_battery, pick, place, charge]

The docstring is the prompt. The LLM never sees your function body, only its name, arguments and docstring. Write them for the model. And only expose the functions you want the LLM to reach.

Now give R-80 an order and watch it chain tools on its own:

if __name__ == "__main__":
    WORLD.add_robot("r80")
    agent = create_agent(
        model=get_model(),
        tools=make_robot_tools("r80"),
        system_prompt=SYSTEM_PROMPT,
    )
    result = agent.invoke(
        {"messages": [{"role": "user", "content": "Bring the red cube to the workbench."}]}
    )
    for message in result["messages"]:
        message.pretty_print()
    print("\n" + WORLD.render())

2c · RAG: give it a manual

What is RAG?

Retrieval-Augmented Generation: before the LLM answers, retrieve the relevant pieces of your own documents and augment the prompt with them, so the model generates its answer from real facts.

The problem

The LLM was trained on the internet, not on R-80's manual. Ask for its payload and it will guess a plausible, wrong number: a hallucination.

Why not paste everything?

Manuals can be thousands of pages. Too big, slow and expensive for the context window, and the model gets lost in the noise.

RAG

Only send the 2–4 chunks that matter for this question. Accurate, cheap, and you can cite the source.

It works in two phases. Indexing happens once: load the documents, split them into chunks, turn each chunk into a vector with an embeddings model and store the vectors. Retrieval happens for every question: embed the question the same way, find the nearest chunks, and put them in the prompt. Try it:

Classic RAG vs agentic RAG

Classic

Always retrieve, then answer. Simple, but it searches the manuals even for "hello".

Agentic (what we build)

Retrieval is a tool. The agent decides when to search and what to search for, and can search again if the first result wasn't enough.

R-80 with RAG

We wrap the retriever as a search_manuals tool. The system prompt tells R-80 to check the manuals before anything risky:

def build_manual_tool(k: int = 3):
    """Embed the manuals once and return a `search_manuals` tool."""
    splitter = RecursiveCharacterTextSplitter(chunk_size=400, chunk_overlap=50)
    chunks = splitter.split_documents(load_manuals())
    store = InMemoryVectorStore.from_documents(chunks, get_embeddings())  # text -> vectors
    retriever = store.as_retriever(search_kwargs={"k": k})               # top-k nearest chunks

    @tool
    def search_manuals(query: str) -> str:
        """Search the R-80 service manual and the lab safety rules (specs, limits, zones, error codes)."""
        hits = retriever.invoke(query)
        return "\n\n".join(f"[{d.metadata['source']}] {d.page_content}" for d in hits)

    return search_manuals

// SAVE POINT

  • Provider = who runs the LLM. Swapping it is one string: "provider:model".
  • The system prompt sets identity, facts, rules and output format, on every turn.
